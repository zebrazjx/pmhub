# 发现与问题定义

按需用于机会发现、用户研究、JTBD、研究综合、机会树和问题简报。目标是降低“做错问题”的风险，不是证明既定方案正确。

## 1. 机会信号台账

先把反馈、请求和想法拆成可比较的信号。每条至少记录：

| 字段 | 要求 |
|---|---|
| Signal ID | 稳定标识，便于回链 |
| 来源与日期 | 用户访谈、行为数据、支持单、销售、市场、内部建议等 |
| 目标人群 | 角色、场景、产品成熟度等与行为有关的特征 |
| 具体情境 | 什么时候、因为什么触发 |
| 观察／原话 | 区分观察事实和用户表达；只在有原文时使用引号 |
| 当前行为 | 用户今天如何完成任务，包括不用产品的方式 |
| 阻碍与后果 | 时间、金钱、错误、风险、情绪或机会成本 |
| 频率／范围 | 有数据写数据，没有则标未知 |
| 替代／变通 | 已采用的工具、人工流程、放弃行为 |
| 证据强度 | 强／中／弱，并说明样本和偏差 |
| 关联机会 | 暂定问题簇，不写成功能名 |

同一个大客户的十次请求不是十个独立样本；一次问卷的百个“想要”也不等同于百次真实行为。记录来源相关性，避免伪造信号量。

### 证据强度

- **强**：可重复观察到的目标行为、交易／成本、可靠日志、多个独立来源收敛。
- **中**：具体过去事件、工单、访谈叙述、局部样本中的重复模式。
- **弱**：未来意向、偏好投票、未经验证的销售转述、单个高层意见。

强弱取决于要做的决定。低成本、可逆试验可以接受较弱证据；高成本或不可逆投入需要更强证据。

## 2. 研究计划从决定倒推

不要从“我们要访谈十个人”开始。按以下顺序：

1. **决定**：研究完成后要选择什么？
2. **最危险未知**：哪个未知一旦为假就会推翻决定？
3. **所需证据**：行为、态度、可用性、规模、因果还是技术可行性？
4. **方法**：选择最能回答该未知的方法。
5. **样本与招募**：谁必须被纳入，谁要排除，哪些关键分层要覆盖？
6. **分析与停止规则**：如何综合、何时继续、何时停止或换方法？
7. **伦理与隐私**：同意、录音、敏感数据、保存范围与匿名化。

### 方法选择

| 需要知道 | 优先方法 | 不能单独证明 |
|---|---|---|
| 过去如何完成任务、为何切换 | 半结构化访谈、情境访查、日志回放 | 市场规模、普遍性 |
| 在界面中哪里失败 | 任务型可用性测试、观察 | 长期价值与留存 |
| 行为有多普遍 | 产品分析、结构化调查、样本统计 | 深层动机、因果 |
| 哪个方案导致结果变化 | 随机实验或合适的准实验 | 机制为何发生 |
| 技术／运营能否成立 | 原型、Wizard-of-Oz、可行性尖峰 | 用户愿意长期采用 |
| 是否愿意付出真实代价 | 预购、排队、配置、迁移、试点承诺 | 全量市场需求 |

AI 生成的模拟用户只能帮助预演提纲或发现盲点，不能冒充真实用户证据。

## 3. 访谈设计与执行

### 提纲结构

1. 开场：目的、时长、录音和隐私授权；说明测试的是产品／假设，不是参与者。
2. 背景：角色、环境、任务频率和决策权。
3. 最近一次：让对方讲一个具体、最近、完整的事件。
4. 时间线：触发→寻找→比较→选择→使用→结果。
5. 阻碍：最难处、错误、等待、绕路、谁被牵涉。
6. 替代方案：现有工具、人工操作、不处理的后果、已付成本。
7. 结果：用户如何判断“完成得好”。
8. 结束：遗漏、可联系的相似参与者、后续同意。

### 提问规则

- 优先“上一次发生时你怎么做”，少问“以后会不会用”。
- 追问具体例子、动作、时间、代价与权衡，不把赞美当作需求证据。
- 不在研究访谈里推销方案；概念测试要明确区分探索段和评价段。
- 不诱导用户接受团队词汇。先记录原词，再做统一编码。
- 研究者少说，参与者多讲；但不要为了比例牺牲必要澄清。

## 4. JTBD 表达

JTBD 用来解释用户在特定情境下寻求的进展，而非给人格贴标签。

基础格式：

> 当 `[触发情境／约束]` 时，我想要 `[可观察的进展]`，从而 `[更高层结果]`。

补充字段：

- 功能进展：任务上要完成什么；
- 情绪进展：希望避免或获得什么感受；
- 社会进展：希望他人如何看待自己；
- 当前“雇用”的方案；
- 推动力：旧方式的痛苦、新方式的吸引；
- 阻力：现有习惯、新方式的焦虑；
- 成功标准：用户能观察到的结果。

质量检查：没有产品名；情境足够具体；描述进展而非功能；可以解释用户为何在某刻改变行为。

## 5. 研究综合

### 原子证据卡

每张卡只放一个观察或观点：

```text
Evidence ID:
参与者／来源（匿名）：
人群与情境：
观察或原话：
发生了什么：
造成的后果：
初步解释：
替代解释：
关联 Signal ID：
```

综合步骤：

1. 分离原始证据和研究者解释；
2. 按行为、触发、阻碍或结果聚类，不按预设功能聚类；
3. 寻找收敛、矛盾、极端案例和未覆盖人群；
4. 为每条洞察回链证据卡，注明样本边界；
5. 写出“因此可能意味着”以及可证伪的下一步；
6. 不用任意出现次数自动决定重要性，结合严重度、战略相关性和证据独立性。

洞察格式：

> 对 `[人群]` 而言，在 `[情境]` 下，`[行为／阻碍]` 导致 `[后果]`。我们基于 `[证据范围]` 认为 `[解释]`，但 `[替代解释／样本限制]` 仍待验证。

## 6. 机会树

适合在一个明确结果下组织发现，不适合拿来装饰既定功能路线图。

```text
目标结果（一个、可观测）
├─ 机会 A：用户需要／痛点／愿望
│  ├─ 子机会 A1
│  │  ├─ 方案 1
│  │  │  └─ 最危险假设 → 测试
│  │  └─ 方案 2
│  └─ 子机会 A2
└─ 机会 B
```

规则：

- 顶部是结果，不是项目名；机会层使用用户语言且相互尽量不重叠。
- 从研究中生长机会分支；不能从团队功能清单反推“用户问题”来美化它。
- 对优先机会产生多个性质不同的方案，再比较最危险假设。
- 测试结论更新证据和树；失败的方案可以删除，机会不因此自动失效。

## 7. 问题简报与机会门

问题简报至少回答：

- 哪类用户在什么情境遇到什么阻碍；
- 今天如何解决，付出什么代价；
- 证据来自哪里，范围和局限是什么；
- 若解决，用户结果和业务结果如何变化；
- 为什么现在；不做的后果；
- 最危险的价值、可用性、可行性、商业可行性、合规／伦理假设；
- 明确不解决什么；
- 下一步选择：停止、补研究、小试验、进入方案探索。

### 机会门判断

不输出虚假的总分。按维度给 `支持／反对／未知`：

1. 问题真实性和严重度；
2. 目标人群规模或战略价值；
3. 与战略和能力的匹配；
4. 可观测的用户／业务结果；
5. 解决空间与替代方案；
6. 关键风险是否能以合理成本验证。

结论必须是有条件的：`继续探索`、`受控验证`、`进入交付定义`、`暂缓` 或 `停止`，并写清改变结论所需的新证据。
