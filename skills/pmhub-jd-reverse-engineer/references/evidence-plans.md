# 证据建设方案

只生成用户要求的部分。所有证据规格都必须服务于已提炼的三个核心任务。本文件用于确定学到什么深度、做什么产物才足以证明能力；具体课程、练习、项目执行和进度维护交给 `pmhub-ai-learning-coach`。

## 从 JD 倒推学习

把每个知识缺口拆成三层：

| 层级 | 要回答什么 | 合格证据 |
|---|---|---|
| 原理 | 它怎样工作、能力边界和常见失败是什么？ | 能用目标岗位的例子解释关键机制与错误来源 |
| 产品决策 | 何时使用，何时不用；效果、延迟、成本、安全如何取舍？ | 一份选型／权衡表或决策记录 |
| 实践验证 | 能否搭最小链路、构造样本、读日志并比较结果？ | 可运行实验、测试集、评测报告和失败复盘 |

例如 RAG：

- 原理：切分、Embedding、召回、重排、上下文与生成；
- 产品决策：何时用 RAG，知识更新、权限、引用、延迟与成本怎样设计；
- 实践：构造目标场景测试集，比较召回、答案／引用质量、延迟和成本，并分析 Bad Case。

### 证据规格规则

- 先补会阻断三个核心任务的 P0 缺口，再补区分度高的 P1，最后才是扩展知识。
- 每项写明“为什么与 JD 有关、要产出什么、怎样验收、预计投入”。
- 7 天适合完成概念校准与小实验；15 天适合形成一个可讲清的闭环；30 天适合做一轮真实访谈、原型、评测和迭代。不要承诺 30 天替代多年实战或硬年限。
- 学习结束条件不是“看完课程”，而是能解释、能决策、能验证。
- 将上述期限仅作为范围约束，输出缺口、目标深度、替代证据与验收标准；进入学习教练后由其统一生成周计划，JD 组件不另排一套课程。

## 从 JD 倒推项目

项目必须模拟目标岗位的完整责任链：

> 真实用户与任务 → 问题证据 → 数据／模型／规则方案 → 产品交互与人工边界 → 评测集 → Demo／受控试用 → 结果 → 失败复盘

项目 brief 至少约定以下交付与验收项；其中产物尚未完成时，必须标为待建设证据：

1. 用户、触发情境、现有做法、痛点与问题证据；
2. 为什么需要 AI，以及被比较过的更简单方案；
3. 数据来源、模型／RAG／工具／规则分工和权限边界；
4. 主流程、异常流程、人工确认／接管与降级；
5. 含正常、边界和高风险样本的小型评测集；
6. 质量、任务结果、延迟、成本与安全的验收口径；
7. 可运行 Demo、测试日志、版本记录和至少一类真实失败；
8. 当前能证明什么、不能证明什么、下一步验证什么。

只做一个对话框或调用一次 API，不足以证明产品能力。没有真实线上数据时，可以用原始计数、受控任务测试和用户可用性反馈，但必须准确标记为 Demo／离线测试／受控试用，不能冒充业务增量。

项目选题优先复用用户已有的行业、流程或用户资源，让旧经验成为领域证据：

| 已有背景 | 更自然的项目桥梁 | 重点补的证据 |
|---|---|---|
| C 端／设计／用研 | 通用 AI 应用、多模态创作 | 模型边界、AI 原生交互、评测 |
| B 端／SaaS／实施 | 企业 Agent、知识库、客服销售 | RAG、工作流、权限、交付与效果评测 |
| 开发／数据 | Agent／模型平台、开发者工具 | 场景判断、开发者体验、商业结果 |
| 运营／电商／广告／增长 | 营销、搜索推荐或内容 AI | 系统设计、实验、可运行原型 |
| 医疗／法律／金融／教育 | 对应行业 AI | 专业任务、合规、专业评测与人工责任 |
| 汽车／硬件／工业 | 智能硬件、多模态交互 | 数据闭环、端云约束、可靠性与安全 |

## 从 JD 倒推简历

先确定首屏必须证明的三项能力及各自最强证据。每条经历优先使用：

> 场景／问题 + 个人动作与关键判断 + 技术／协作／产物 + 真实结果或验证证据

真实性规则：

- 只使用与事实一致的 JD 标准词；做过 FAQ 不能写成 RAG，参与不能写成主导，Demo 不能写成上线。
- 原始数字、时间、范围和个人贡献保持不变。没有可信数字时，用可核验产物、样本、验收或决策代替。
- 若用户只给一条模糊经历，先在现有事实内改写；只有缺失信息会显著改变真实性或结果时才追问。
- 不机械堆砌关键词。技能词必须落到“用它解决了什么问题、做了什么判断、怎样验证”。

用户要求模板时可使用占位符；用户要求直接改写时不得凭空补占位指标。

## 从 JD 倒推面试

准备五类故事，每类映射一个核心任务或风险：

| 故事 | 必须讲清 | 常见追问 |
|---|---|---|
| 0→1 | 如何发现问题、收敛范围、定义首版和成功标准 | 为什么先做这个？砍掉了什么？ |
| 技术取舍 | 候选方案、约束、选择标准和反事实条件 | 为什么不用更简单／更强的方案？ |
| 跨团队冲突 | 各方目标、分歧证据、个人责任与裁决机制 | 你真正做了什么？谁做最终决定？ |
| 数据／评测 | 样本、指标、基线、失败分类和迭代 | 指标为何可信？Bad Case 怎样改变方案？ |
| 失败复盘 | 首次偏离、损失、修复、预防和未解决边界 | 再来一次会怎样做？ |

每个故事使用：约束 → 个人判断 → 关键行动 → 可核验结果 → 失败／边界 → 下一步。只有用户提供真实素材时才生成个人故事；否则输出“需要寻找的经历证据”和追问清单。
