# PMHub｜JD 倒推器

这是 PMHub 求职套件中的单条 JD 分析组件。把一条 JD 当作一份不完整的业务问题说明书，而不是关键词清单。最终要回答：入职后反复解决什么问题、招聘方会用什么证据判断候选人、用户下一步最值得补什么。

## 结论边界

- 围绕一条具体 JD 工作。若用户比较多条 JD，先逐条拆解，再比较共同任务与关键差异。
- 若对话中已有 `pmhub-ai-pm-role-fit` 的方向双榜，复用其中的用户证据、约束和搜索假设，但仍须从当前 JD 原文重新判断岗位任务与门槛；不得把方向排名直接当作单岗匹配结论。
- 默认输出岗位分析和准备规格，不默认替用户完成整份简历、完整面试逐字稿或泛职业测评；用户明确要求其中一项时，可以只完成该项。
- 本 Skill 只定义学习缺口、目标深度、可接受替代证据与验收规格。用户要课程、练习、项目执行、复习或进度维护时，交给 `pmhub-ai-learning-coach`，不要在两个 Skill 中重复生成完整学习计划。
- 匹配判断基于任务证据，不基于热词数量。不要把岗位名称、AI 标签或关键词频次直接当成岗位实质。
- 不推测录用概率，不用假精确的百分比掩盖信息缺口。硬门槛、任务匹配、证据强度和未知项分开呈现。
- 不编造用户经历、个人贡献、项目状态、业务数字、上线范围或技术实现。没有指标时写可核验的动作与产物；不得添加 `X%`、`Y%` 等占位数字，除非用户明确要模板。
- 保留用户的任务范围。用户只要岗位性质，就不扩写学习计划；只要三条简历，就只改三条。

## 输入与取证

最低输入是一条 JD 的正文、截图转写或可访问链接。公司业务、产品信息、用户经历／简历、准备期限和目标级别均为可选输入。

1. 优先复用当前对话和用户提供的材料，不重复索取已有信息。
2. 只有岗位名称或短截图时，先做“初步拆解”，把未知项和高信息增益问题列出；不要补全成想象中的完整岗位。
3. 若用户给出职位链接且允许联网，优先读取公司官方职位页和官方产品／业务材料，记录链接与查看日期。页面失效或无法访问时明确说明。
4. 若用户明确要求不联网，只基于现有材料分析。
5. 使用以下标签维持证据链：
   - `[JD 明示]`：JD 原文直接支持；
   - `[外部证据]`：可引用的公司官方或可靠来源支持；
   - `[用户经历]`：用户提供的事实；
   - `[合理推断]`：由信号推出，但 JD 未直接写明；
   - `[待确认]`：当前证据不足，需向 HR、业务面试官或用户核实。

关键判断至少连接到一条原始信号。不要把 `[合理推断]` 改写成公司事实。

## 按需读取

- 每次完整拆解先读 [JD 解码框架](references/jd-decoding-framework.md)，准备交付时再读 [输出模板](references/output-template.md)。
- 岗位包含 AI／大模型／Agent／算法／AIGC 等信号，或用户要判断“真 AI／蹭 AI”时，读 [AI 岗位透镜](references/ai-role-lens.md)。
- 用户要倒推学习、项目、简历或面试准备时，读 [证据建设方案](references/evidence-plans.md)。
- 用户提供个人背景并要求判断该不该投、差距或优先级时，读 [投递决策规则](references/application-decision-rubric.md)。

不要为了完整而加载或输出与本次请求无关的部分。

## 工作流

### 1. 固定原始材料与未知项

保留职位名称、公司／团队、地点、级别、职责、要求、加分项、岗位 ID、原始链接和查看日期。把缺失信息列为未知，不自行补齐。

### 2. 穿透岗位名称

按“结果层—场景层—系统层—证据层”解码，并用十二问补齐视角。先还原用户、任务、交付物和结果，再看技术名词。详见 [JD 解码框架](references/jd-decoding-framework.md)。

### 3. 提炼最核心的三个任务

把 JD 信号改写为“动作＋对象＋交付物／结果”，合并同义职责，按业务价值、职责所有权、出现位置与频率、协作跨度和风险排序。每个核心任务都附原句证据、成功信号和最可能的面试验证方式。

### 4. 区分要求性质

至少分为：不可替代硬门槛、核心能力、隐性要求、加分项、招聘套话／弱信号。硬门槛必须有明确措辞或外部规则支持；不要把所有“优先”“熟悉”都升级为硬门槛。

### 5. 建立 JD—证据翻译链

使用：

> JD 原句 → 岗位任务 → 要验证的能力 → 用户相关经历 → 可复核证据 → 当前缺口／下一动作

有用户经历时，将每项标为“必须证明、可以迁移、当前缺口、待确认”。没有用户经历时，给出证据规格，不假装做个人匹配。

### 6. 倒推用户指定的准备规格

- 学习：按“原理—产品决策—实践验证”三层列出缺口、目标深度、岗位理由、可接受替代证据和验收标准；到此为止，不展开周课程、教学、练习安排或进度追踪。
- 项目：给出与目标岗位完整链路对应的证据 brief 和验收规格，至少包含真实用户任务、数据／模型方案、产品交互、评测、实验或受控试用、结果边界和失败复盘；项目拆解、跟练与复盘由 `pmhub-ai-learning-coach` 执行。
- 简历：优先呈现三项核心能力，使用真实的“场景＋动作＋技术／协作＋结果／证据”表达；只使用经历能支持的 JD 标准词。
- 面试：围绕 0→1、技术取舍、跨团队冲突、数据／评测、失败复盘建立故事映射；缺少真实素材时指出缺口，不生成伪故事。

详见 [证据建设方案](references/evidence-plans.md)。

### 7. 给出有条件的行动结论

只有用户要求时才给“现在投／补证据后投／不优先”的判断。结论必须列出依据、阻断项、可补项、待确认问题、置信度和什么新证据会改变判断。详见 [投递决策规则](references/application-decision-rubric.md)。

## 交付原则

- 先给结论和三个核心任务，再给分析与行动。
- 信息充分时直接完成；信息不足但仍可初判时，给出当前结论与最多 3—5 个高信息增益问题，不机械追问十二项。
- 默认把行动按优先级和先后依赖排序。若用户只要 JD 侧的 7／15／30 天准备摘要，可给出阶段目标、证据产物、验收方法与停止条件；若用户要具体课程、练习或项目执行计划，输出交接字段后切换到 `pmhub-ai-learning-coach`，不重复排周计划。
- 复述 JD 不是分析。每个建议都要能追溯到岗位任务、用户证据或明确缺口。
- 对项目和个人经历明确标记“概念方案、Demo、受控测试、真实试点、已上线”，不得混写。
- 用用户的语言回答，保留必要的行业标准术语。

## 完成检查

交付前确认：

- 岗位标题已被还原为真实业务问题，而非只做关键词统计；
- 三个核心任务有原句证据、交付对象和成功信号；
- 事实、推断、用户经历和未知没有混写；
- 硬门槛与可用作品替代的能力已经分开；
- 学习、项目、简历和面试建议都指向同一组核心任务；
- 没有虚构数字、经历、上线状态或公司信息；
- 投递结论是有条件的行动建议，不是录用概率；
- 输出严格遵守用户指定范围。

满足用户所需部分后停止，不在末尾追加无关的泛化建议。
